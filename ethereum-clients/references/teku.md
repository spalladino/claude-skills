# Teku (consensus)

Java 25 (Gradle multi-module), Ethereum consensus client: beacon node + validator client. GitHub: https://github.com/Consensys/teku (local clone: `~/Projects/ethereum/teku`, blobless partial clone, read-only). Default branch `master`.
Latest release tag: `git tag -l '2*' --sort=-v:refname | head` (calendar versions `YY.M.patch`, e.g. 26.10.3; plain `git tag --sort=-creatordate` is polluted by ancient `v0.x` tags). Release branches exist as `origin/26.10.2` etc. Snapshot reviewed: master @ f78ecce75b (2026-11-03), already includes Gloas (ePBS) endpoints.
All paths below are relative to the repo root. Unverified claims are marked (unverified).

## 3. Behaviour

### Error format and status codes
- Error body (all handlers): `{"code": <int>, "message": "<text>"}` (`HttpErrorResponse`, `CoreTypes.HTTP_ERROR_RESPONSE_TYPE`). Teku adds no `stacktraces` field.
- Exception mapping (registered in `JsonTypeDefinitionBeaconRestApi.create`): `ChainDataUnavailableException` -> **204** (empty body; "chain has not reached genesis / store not available"); `NodeSyncingException`, `ServiceUnavailableException` -> **503** "Beacon node is currently syncing and not serving requests" (`RestApiConstants.SERVICE_UNAVAILABLE`); `BadRequestException`/`JsonProcessingException`/`IllegalArgumentException` -> **400** (message = exception message, e.g. `Invalid state ID: foo`, `Could not read path parameter ...`); `ContentTypeNotSupportedException` -> **415** (unsupported request Content-Type); `MissingDepositsException` -> 500. Anything unhandled -> **500** `"An unexpected error occurred"` (`infrastructure/restapi/.../DefaultExceptionHandler.java`). Not-found data: handlers return `AsyncApiResponse.respondNotFound()` -> **404** `{"code":404,"message":"Not found"}`.
- 503 sources: (a) `isSyncing()` precheck in handlers: `PostBlock*`, `PostBlindedBlock*`, `GetProposerDuties(V2)`, `PostAttesterDuties`, `PostSyncDuties`, `PostValidatorLiveness`, `PostPayloadTimelinessCommitteeDuties` (`SyncDataProvider.isSyncing()` = sync state != IN_SYNC, so START_UP, SYNCING, OPTIMISTIC_SYNCING, AWAITING_EL all count); (b) `NodeSyncingException` from `beacon/validator/.../ValidatorApiHandler` (attestation data, block production, aggregates, sync contributions ...), including **when the head/parent block is optimistically validated** (`createBlock`, `createAttestationData` -> "Unable to produce block ... parent has optimistically validated payload"); (c) `/eth/v1/node/health` returns 503 only if store unavailable or `syncProvider.getRejectedExecutionCount() > 0`.
- `/eth/v1/node/health`: 200 in sync; while syncing returns **206** by default or the code in `?syncing_status=` (100-599, else 400 "Invalid syncing status code"); `Cache-Control: max-age=0`. `/teku/v1/admin/readiness` (503 if syncing, store missing, EL unavailable, or optional `target_peer_count`, `require_prepared_proposers`, `require_validator_registrations` unmet) and `/teku/v1/admin/liveness` are the k8s-style probes.
- `/eth/v1/node/syncing` (`v1/node/GetSyncing`): `head_slot, sync_distance, is_syncing, is_optimistic, el_offline`. Quirk: `sync_distance`/`is_syncing` are computed from `highestSlot - currentSlot` only when sync state != IN_SYNC AND a peer-highest slot is known, so `is_syncing` can be false during START_UP with no peers. `el_offline` = `!ExecutionClientDataProvider.isExecutionClientAvailable()`.
- Block publishing result (`v1/beacon/AbstractPostBlock.processSendSignedBlockResult`): accepted -> 200; rejected-but-published to gossip -> **202**; rejected and not published -> **500** with the rejection reason (spec says 400; Teku uses 500). `POST /eth/v2/beacon/blocks` takes `?broadcast_validation=` (default `gossip`; levels in `BroadcastValidationLevel`: NOT_REQUIRED, EQUIVOCATION, GOSSIP, CONSENSUS, CONSENSUS_AND_EQUIVOCATION) and optional `Eth-Builder-Url` header. v1 POST always uses GOSSIP. `produceBlockV3` returns 400 for Gloas+ slots ("use produceBlockV4"), 500 "Unable to produce a block" if empty.
- `MAX_BLS_MESSAGES_PER_REQUEST = 5000` in `PostBlsToExecutionChanges`.

### state_id / block_id resolution
- `data/provider/src/main/java/tech/pegasys/teku/api/AbstractSelectorFactory.java`: `0x...` -> state root (state_id) or block root (block_id); else keyword `head|genesis|finalized|justified`, else parsed as slot (`UInt64.valueOf`); anything unparsable -> 400 `Invalid state ID: x` / `Invalid block ID: x`. Concrete selectors: `stateselector/StateSelectorFactory`, `blockselector/BlockSelectorFactory`, `blobselector/{BlobSelectorFactory,BlobSidecarSelectorFactory}`, `datacolumnselector/`, `executionpayloadselector/`.
- Slot ids are resolved against the *current head chain*: slot > head slot -> empty -> 404. For block_id by slot, an empty slot returns 404 (`getBlockAtSlotExact`); for state by slot Teku returns the (regenerated) state at that exact slot even if the slot was skipped.
- Metadata: `execution_optimistic` = head optimistic OR block/state root optimistic; `finalized` = `slot <= start_slot(finalized_epoch)` (`CombinedChainDataClient.isFinalized`). Quirk: `justified` state selector always reports `finalized=false`; `genesis` is always `optimistic=false, finalized=true`; `finalized` selector uses `isChainHeadOptimistic()` for optimistic (finalized cannot be optimistic unless head is). Handlers set `Eth-Consensus-Version` response header (lowercase milestone) where the body is fork-dependent.
- Root-based lookups also resolve non-canonical blocks/states that are still in the hot store; canonical flag exists on the internal metadata (`BlockAndMetaData`) but is not part of the API response.

### State availability / historical states
- Hot (unfinalized) states are served from `Store`; finalized state history depends on `--data-storage-mode` (`storage/.../server/StateStorageMode.java`): `ARCHIVE` (all finalized states reachable: stores a finalized state every `--data-storage-archive-frequency` slots, default 2048 (`StorageConfiguration.DEFAULT_STORAGE_FREQUENCY`), others regenerated by replaying blocks), `PRUNE` (only the latest finalized state; older slots -> 404), `MINIMAL` (like prune and additionally prunes blocks older than `MIN_EPOCHS_FOR_BLOCK_REQUESTS`, 33024 on mainnet/hoodi per network yaml). Default is `NOT_SET`, resolved in `StorageConfiguration.determineStorageDefault`: explicit flag > mode file stored in the data dir (`DatabaseStorageModeFileHelper`) > existing DB without file => PRUNE (with warning) > fresh DB => **MINIMAL**.
- State regeneration: `CombinedChainDataClient.getStateAtSlotExact` -> `regenerateStateAndSlotExact` (replays blocks from latest stored finalized state). Time-bounded by hidden `--Xdata-storage-state-rebuild-timeout-seconds` (default 120, `DEFAULT_STATE_REBUILD_TIMEOUT_SECONDS`; warns outside 10-300). Archive state pruning: hidden `--Xdata-storage-archive-finalized-states-retained` (default 0 = keep all), `--Xdata-storage-state-pruning-interval/limit` (5 min / 1).
- Other storage options: `--data-storage-non-canonical-blocks-enabled` (default false; needed for /teku/v1/beacon/blocks/{slot} to show forks), `--Xdata-storage-blobs-archive-path`, pruning intervals: blocks 15 min/5000, blob sidecars 1 min/12, data columns 1 min/64 (hidden `--Xdata-storage-*-pruning-*`).
- Debug state `/eth/v2/debug/beacon/states/{state_id}`: JSON or SSZ with `Eth-Consensus-Version`; for non-hot slots goes through the same regeneration path.

### Content negotiation
- `Accept: application/json` (default) or `application/octet-stream` for SSZ on endpoints that declare it (blocks, states, blobs, blob/column sidecars, produce block, light client...). `ContentTypes.getResponseContentType` uses MIMEParse best match; an unsupported/unmatched Accept silently **falls back to the endpoint default (JSON)** instead of 406 (`EndpointMetadata.selectContentType`); explicit 406 exists only where a handler codes it (e.g. `GetExecutionPayloadBid`, advertised via `withNotAcceptableResponse()` on produce-block/debug sidecars/some state endpoints).
- Requests: JSON or SSZ for block POSTs; unsupported Content-Type -> 415. `Eth-Consensus-Version` request header: marked required in OpenAPI (`headerRequired`), but JSON bodies without it fall back to slot-based schema detection (`MilestoneDependentTypesUtil.headerBasedSelectorWithSlotFallback`); SSZ bodies need it -> 400 `Missing required header value for (Eth-Consensus-Version)` (SSZ case not exercised in this review, unverified). Produce-block response headers: `Eth-Consensus-Version`, `Eth-Execution-Payload-Blinded`, `Eth-Execution-Payload-Value`, `Eth-Consensus-Block-Value` (`RestApiConstants.HEADER_*`).

### Blobs / data columns (Deneb -> Fulu PeerDAS)
- Retention: `MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS` 4096 and `MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` 4096 epochs (mainnet.yaml). Pruners: `storage/.../server/pruner/{BlobSidecarPruner,DataColumnSidecarPruner}.java` (data column prune slot = start of epoch `current - (min_epochs+1)`; also an archiver of columns "to proofs"; earliest custody slot maintained by `DasCustodyBackfiller`).
- `GET /eth/v1/beacon/blob_sidecars/{id}` (deprecated): pre-Fulu reads stored sidecars (falls back to blob archive if configured); for Fulu+ blocks sidecars are *reconstructed* (`BlobSidecarReconstructionProvider`). Block unknown -> 404; block exists but data pruned/unavailable -> **200 with `data: []`** (not 404). Block with zero commitments -> 200 empty.
- `GET /eth/v1/beacon/blobs/{id}` (`GetBlobs`, `BlobSelectorFactory`): Fulu+ blocks use `BlobReconstructionProvider.reconstructBlobs`: tries (1) extension reconstruction from first 50% of columns, (2) crypto (erasure) reconstruction using all locally stored columns, (3) network reconstruction by downloading columns from peers - only if `--rest-api-getblobs-sidecars-download-enabled` (default false; timeout `--rest-api-getblobs-sidecars-download-timeout` default 5 s). If all fail -> 200 with empty list. So a non-supernode (custodies only a subset of columns) generally returns empty `data` unless it has >=50% columns or download is enabled. Supernode = custody all groups: `--p2p-subscribe-all-subnets-enabled` (`SuperNodeSupplier`/`MiscHelpersFulu.isSuperNode`); hidden `--Xcustody-group-count-override`.
- `GET /eth/v1/debug/beacon/data_column_sidecars/{id}`: Fulu+ only (pre-Fulu block -> 404); returns only columns this node custodies/stored; no ordering guarantee; empty list for Fulu blocks without blobs.
- EL-assisted recovery: `DataColumnSidecarELManagerImpl` uses `engine_getBlobsV1/V2`; disable with hidden `--Xdas-disable-el-recovery`.

### SSE (`/eth/v1/events`)
- Topics = `data/serializer/.../api/response/EventType.java`: head, head_v2, block, attestation, single_attestation, voluntary_exit, finalized_checkpoint, chain_reorg, sync_state, contribution_and_proof, bls_to_execution_change, blob_sidecar (to be removed at Gloas), data_column_sidecar, attester_slashing, proposer_slashing, payload_attributes, block_gossip, execution_payload, execution_payload_gossip, execution_payload_available, execution_payload_bid, payload_attestation_message, proposer_preferences, fast_confirmation. (No `light_client_*` topics.)
- Query `?topics=a&topics=b` (or comma separated); empty -> 400 "No topics supplied"; unknown -> 400 "Invalid topic: x" (checked before stream starts).
- Per-subscriber queue (`EventSubscriber`): limit `--Xrest-api-max-pending-events` default **250** (`DEFAULT_MAX_EVENT_QUEUE_SIZE`); when exceeded, events still queue for a 1000 ms tolerance (`EXCESSIVE_QUEUING_TOLERANCE_MS`), then the client is disconnected. Keep-alive: SSE comment every 30 s if idle.

### Transport limits
- No rate limiting anywhere in the Beacon REST API (verified: none in `beaconrestapi`/`infrastructure/restapi`). Async request timeout 30 s (`--Xrest-api-async-timeout-seconds`, `DEFAULT_REST_API_ASYNC_TIMEOUT`); max URL length 65535 (`--Xrest-api-max-url-length`); validator-api thread pool min(10, cores) (`--Xrest-api-validator-threads`); optional Jetty virtual threads (`--Xrest-api-virtual-threads-enabled`, default false, 200 concurrent tasks).
- Binding: `--rest-api-enabled` default false (becomes true if `--rest-api-port` is given without enabled flag; see `BeaconRestApiOptions.configure`); `--rest-api-interface` default `127.0.0.1`; `--rest-api-port` 5051.
- Host allowlist: `--rest-api-host-allowlist` default `127.0.0.1,localhost` (use `*` for any); mismatch -> **403** "Host not authorized" via Javalin `ForbiddenResponse` (not the JSON error shape) (`infrastructure/restapi/.../HostAllowlistHandler.java`, tested by `RestApiHostAllowlistIntegrationTest`). CORS: `--rest-api-cors-origins` default empty = none; `*` allows any (`RestApiBuilder.configureCors`).

## 4. Engine API client side

- Code: `ethereum/executionclient` (transport + JSON-RPC methods) and `ethereum/executionlayer` (logic). Transports chosen from `--ee-endpoint` scheme (`ExecutionEngineClientFactory`): `http(s)://` (OkHttp), `ws(s)://`, `file://` (IPC unix socket). Wrapped by `MetricRecordingExecutionEngineClient` and `ThrottlingExecutionEngineClient` (max `MAXIMUM_CONCURRENT_EE_REQUESTS = 5` concurrent, `Constants.java`).
- Per-milestone method versions: `MilestoneBasedEngineJsonRpcMethodsResolver` -> Bellatrix newPayloadV1/getPayloadV1/FCU V1; Capella V2/V2/V2; Deneb V3/V3/V3; Electra newPayloadV4, getPayloadV4, FCU V3; Fulu newPayloadV4, getPayloadV5, FCU V3; Gloas/Heze newPayloadV5, getPayloadV6, FCU V4 + `engine_getPayloadBodiesByHashV2`. Method classes in `executionclient/methods/Engine*V*.java`. `engine_getBlobsV1/V2`, `engine_exchangeCapabilities`, `engine_getClientVersionV1` are called directly via `ExecutionEngineClient` (`ExecutionClientHandlerImpl.engineGetBlobsV1/V2`).
- Timeouts (`ethereum/spec/.../config/Constants.java`, `AbstractExecutionEngineClient`): newPayload/forkchoiceUpdated `EL_ENGINE_BLOCK_EXECUTION_TIMEOUT` = 8 s; getPayload 2 s; getBlobs 2 s; getPayloadBodies 2 s; exchangeCapabilities 1 s; getClientVersion 1 s; other 1 s (`EL_ENGINE_NON_BLOCK_EXECUTION_TIMEOUT`). Default OkHttp call/read timeout 1 s (`OkHttpClientCreator`).
- Retries: no generic retry loop in the client. A failed FCU used for block production is re-sent within the slot (CHANGELOG: "Block production now recovers within the slot when the engine_forkchoiceUpdated call fails"); see `statetransition/.../forkchoice/ForkChoiceNotifierImpl`. Capability exchange: `EngineCapabilitiesMonitor` runs at the first slot and then every 10 epochs (slot index 2 of the epoch); missing EL methods only log a warning (`--exchange-capabilities-monitoring-enabled`, default true).
- Payload status handling (`spec/.../executionlayer/{PayloadStatus,ExecutionPayloadStatus}.java`, `statetransition/.../forkchoice/ForkChoice.java` `importBlockAndState`, `ForkChoicePayloadExecutor`): VALID imports normally; INVALID -> block import fails (`failedStateTransition("Invalid ExecutionPayload: <reason>")`) and `onExecutionPayloadResult(...)` marks the parent/ancestors invalid in proto-array using `latestValidHash`; SYNCING/ACCEPTED ("not validated") -> block imported **optimistically** if the spec's `canOptimisticallyImport` rule allows, else `FAILED_EXECUTION_PAYLOAD_EXECUTION_SYNCING`; transport/JSON error -> `PayloadStatus.failedExecution(cause)` -> `BlockImportResult.failedExecutionPayloadExecution` (block not imported; retried later by sync/gossip fetch). Optimistic head reflected in `is_optimistic` (syncing), `execution_optimistic` flags and sync state `OPTIMISTIC_SYNCING`/`AWAITING_EL`; a validator will not produce blocks/attestations on an optimistic head (503). Post-merge-transition checks in `MergeTransitionBlockValidator`.
- EL availability: `ExecutionClientDataProvider` (fed by `ExecutionClientEventsChannel`) -> `el_offline` in `/node/syncing`, readiness probe.
- JWT: `--ee-jwt-secret-file` (hex 256-bit); if omitted Teku **generates** `ee-jwt-secret.hex` in the beacon data dir (`JwtSecretKeyLoader`) and logs the path; missing file given explicitly -> `InvalidConfigurationException`. `--ee-jwt-claim-id` adds an `id` claim. Tokens are short-lived (EL accepts iat within +-5 s) (`auth/{JwtConfig,Token,SafeTokenProvider}`).
- No `--ee-endpoint`: allowed only pre-merge networks/with stub; (unverified) otherwise Teku logs EL-unavailable and cannot validate payloads.

## 5. Validator client, keymanager, builder/MEV

- Validator client code: `validator/client` (duty loaders/schedulers: `AttestationDutyScheduler`, `BlockDutyScheduler`, `*DutyLoader`; `BlockProductionDutyLoader`), `validator/remote` (REST client to BN, `FailoverValidatorApiHandler`, `SentryValidatorApiChannel`, `typedef/handlers/*Request`), `validator/api` (`ValidatorConfig` with all `DEFAULT_*`), `validator/beaconnode`. Runs in-process with BN by default or standalone via `teku validator-client --beacon-node-api-endpoint(s)=...` (default endpoint `http://127.0.0.1:5051`). VC defaults: SSZ blocks enabled (`--beacon-node-ssz-blocks-enabled` true), POST validators endpoint enabled, doppelganger detection off (`--doppelganger-detection-enabled`), keystore locking on, external signer timeout 5 s, 32 concurrent signer requests, early attestations on.
- Keymanager API: `validator/client/src/main/java/tech/pegasys/teku/validator/client/restapi/ValidatorRestApi.java` + `apis/*` : `/eth/v1/keystores` (GET/POST/DELETE: `GetKeys`, `PostKeys`, `DeleteKeys`), `/eth/v1/remotekeys`, `/eth/v1/validator/{pubkey}/{feerecipient,gas_limit,graffiti,builder_config}` (GET/POST/DELETE) and `/voluntary_exit` (POST). Options (`ValidatorRestApiOptions`): `--validator-api-enabled` (default false), `--validator-api-port` 5052, `--validator-api-interface` 127.0.0.1, `--validator-api-host-allowlist` (127.0.0.1, localhost), `--validator-api-cors-origins`, `--validator-api-docs-enabled`, `--validator-api-bearer-file` (default `<data>/validator/key-manager/validator-api-bearer`, auto-generated token), `--validator-api-keystore-file` + `--validator-api-keystore-password-file`. **TLS is on by default** (`--Xvalidator-api-ssl-enabled` default true): startup fails without a keystore unless SSL is disabled, and disabling SSL is only allowed on 127.0.0.1 (`ValidatorRestApiConfig.build`; override `--Xvalidator-api-unsafe-hosts-enabled`). Bearer auth via `RestApiBuilder.passwordFilePath`; 401/403 per `AuthorizationHandler`. Errors: same `{code,message}` shape (400, 503 "Service unavailable").
- BN-side proposer data: `POST prepare_beacon_proposer` (fee recipient; expires after `PROPOSER_PREPARATION_EXPIRATION_EPOCHS = 3`), `POST register_validator` (expires after 2 epochs) -> `ProposersDataManager` (`statetransition/.../forkchoice/`). Proposer config file: `--validators-proposer-config` (+ `--validators-proposer-config-refresh-enabled`), default fee recipient `--validators-proposer-default-fee-recipient`; builder registration default off (`--validators-builder-registration-default-enabled`, gas limit default 60,000,000).
- Builder/MEV (pre-Gloas, relay API): `--builder-endpoint` (BN). Code: `ethereum/executionlayer/.../ExecutionBuilderModule.java` (decision logic), `ExecutionLayerManagerImpl`, `ExecutionLayerBlockProductionManagerImpl`, `BuilderBidValidatorImpl`, `BuilderCircuitBreakerImpl`; REST client `ethereum/executionclient/.../rest/RestBuilderClient.java` (`BuilderApiMethod`). Timeouts (`Constants`): builder call 8 s, status 1 s, getPayload 3 s, registerValidator 8 s, proposal delay tolerance 1 s. Fallback to local EL payload (always requested in parallel) with metric label `FallbackReason` (`spec/.../datastructures/execution/FallbackReason.java`): not_needed, validator_not_registered, transition_not_finalized, circuit_breaker_engaged, builder_not_available (status check failed), builder_not_configured, builder_header_not_available, local_block_value_won, should_override_builder_flag_is_true, builder_error. Check order in `ExecutionBuilderModule`: transition not finalized -> circuit breaker -> builder missing -> builder unavailable -> validator not registered.
- Bid comparison: `--builder-bid-compare-factor` (BN, default **90** = percent; `BUILDER_ALWAYS` keyword = always take builder bid unless invalid; `ExecutionLayerConfiguration.DEFAULT_BUILDER_BID_COMPARE_FACTOR`). A VC-supplied `?builder_boost_factor=` on `GET /eth/v3/validator/blocks/{slot}` overrides it for that request (`BuilderBoostFactorEvaluator`: 0 = always local, `UInt64.MAX` = always builder, 100 = max profit, otherwise builder wins if `builder_value * factor > local_value * 100`). `shouldOverrideBuilder` from `engine_getPayload` forces local (hidden `--Xuse-should-override-builder-flag`, default true).
- Circuit breaker (`BuilderCircuitBreakerImpl`, hidden flags `--Xbuilder-circuit-breaker-*`): enabled by default; window 32 slots (hard cap 64, must be <= SLOTS_PER_HISTORICAL_ROOT), allowed faults 5 (engaged if unique block roots in window < window - 5), allowed consecutive empty slots 3 (engaged if more than 3). Any exception evaluating it => treated as engaged.
- Gloas (ePBS) replaces relay flow: `GetExecutionPayloadBid`, `PostPublishExecutionPayloadBid`, `--builder-min-bid`, `--p2p-builder-min-bid`, `--builder-boost-factor` (VC, default 100), `--p2p-builder-boost-factor`, `--builder-max-execution-payment`, `--builder-urls` (`BuilderOptions`, `ProposerConfigManager`, `ResolvedBuilderConfig`); BN `--Xconsider-p2p-bids-during-block-production` default true.

## 6. Quirks / deviations from beacon-APIs spec and other clients

- Block POST failure statuses: 500 (not 400) for rejected-and-unpublished blocks; 202 only if published but not imported (`AbstractPostBlock`).
- 204 (not 503/404) for pre-genesis or store-unavailable (`ChainDataUnavailableException`); `GET /eth/v1/node/health` also advertises 204 for pre-genesis.
- Unmatched `Accept` falls back to JSON rather than 406.
- `/eth/v1/beacon/states/{id}` `justified` always `finalized:false`.
- Pruned/unrecoverable blobs yield 200 with `data: []`, not 404; non-supernodes mostly return empty `/blobs`.
- Data column sidecars are served from the debug namespace (`/eth/v1/debug/beacon/data_column_sidecars`), not `/eth/v1/beacon/...`.
- `/eth/v1/debug/beacon/heads` v1 is not registered, only v2; both v1 and v2 `fork_choice` are.
- `/eth/v1/beacon/light_client/*` off by default (hidden flag); no `light_client_*` SSE topics.
- Obol DVT selection endpoints (`beacon_committee_selections`, `sync_committee_selections`) are registered with no backing provider (VC option `--Xobol-dvt-integration-enabled`); (unverified) treat as stubs.
- `/teku/v1/admin/*` and other `/teku/*` endpoints are unauthenticated and obey only the host allowlist; keymanager is separate on 5052 with TLS + bearer.
- Validators refused duties while *any* non-IN_SYNC state (including START_UP), even when sync distance is 0.
- Default storage mode for brand-new DBs is MINIMAL (not archive) - historical states/blocks older than retention return 404.
- Error JSON has only `code` + `message` (no `stacktraces`).
