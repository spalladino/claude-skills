## 1. Orientation

- Workspace crates:

  - `validator_client/` : `src/{cli.rs,config.rs}`, `http_api/` (keymanager + /lighthouse VC API), `validator_services/` (block/attestation/duties/preparation services), `beacon_node_fallback/`, `lighthouse_validator_store/`, `slashing_protection/`, `initialized_validators/`, `doppelganger_service/`, `signing_method/` (local + web3signer).
  - `common/eth2/` (HTTP client + all API types), `common/warp_utils/` (error/rejection mapping, CORS, query parsing), `common/eth2_network_config/`, `common/slot_clock/`, `common/task_executor/`.
  - `consensus/` : `types/` (incl. `core/chain_spec.rs` ChainSpec + presets), `state_processing/`, `fork_choice/`, `proto_array/`, `fast_confirmation/`.
  - Others: `slasher/`, `validator_manager/`, `database_manager/` (offline DB ops, e.g. prune), `lcli/`, `boot_node/`, `testing/`, `book/`.
- CLI flags: BN in `beacon_node/src/cli.rs` (clap builder `Arg::new(..)`, defaults via `.default_value`), consumed in `beacon_node/src/config.rs` (`get_config`). VC uses clap derive in `validator_client/src/cli.rs` (struct `ValidatorClient`) and `validator_client/src/config.rs`. `book/src/help_bn.md` / `help_vc.md` are generated `--help` dumps (grep these for flag text). Default ports: BN HTTP `127.0.0.1:5052` (disabled unless `--http`), metrics `5054` (`--metrics`), P2P TCP+UDP discovery `9000`, QUIC `9001` (`beacon_node/lighthouse_network/src/config.rs`), VC keymanager HTTP `127.0.0.1:5062` (`--http`), VC metrics `5064`. ## 2. Beacon API: where things live

- Everything is in `beacon_node/http_api/src/lib.rs` (`pub async fn serve`, ~3.7k lines). Pattern: each route is a `let get_x = eth_v1.and(warp::path(..))...then(|..| task_spawner.blocking_json_task(Priority::P0|P1, ..))`; all routes are `.uor()`-chained at the bottom into `routes` (GET set, then `warp::post()` set; SSZ-body POSTs gated by `warp::header::exact(CONTENT_TYPE, "application/octet-stream")`). To find a handler: grep the `let get_*`/`post_*` variable name, e.g. `get_beacon_block`, `get_blob_sidecars`, `get_debug_beacon_states`.
- Version filters: `eth_v1 / eth_v2 / eth_v4 = single_version(any_version, Vn)` and `any_version` (handler branches on `EndpointVersion`). Unsupported version => `unsupported_version_rejection` (`version.rs`).

## 3. Behaviour

### Errors and status codes
- All rejections map in `common/warp_utils/src/reject.rs` `handle_rejection` into JSON `{"code": <u16>, "message": "<PREFIX>: ...", "stacktraces": []}` (`eth2::types::ErrorMessage`). Message prefixes are the useful tell: `NOT_FOUND`, `BAD_REQUEST`, `INTERNAL_SERVER_ERROR`, `UNHANDLED_ERROR: <debug of error>` (500), `SERVICE_UNAVAILABLE: beacon node is syncing: head slot is X, current slot is Y` (503), `FORBIDDEN` (403), `UNSUPPORTED_MEDIA_TYPE` (415), `METHOD_NOT_ALLOWED` (405), `UNHANDLED_REJECTION` (500 fallback). Invalid body/query => 400 `BAD_REQUEST: body deserialize error: ...` / `invalid query: ...`; missing header => 400 `BAD_REQUEST: missing Eth-Consensus-Version header`.
- Indexed failures (batch POSTs: attestations, sync committee msgs, slashings, exits) => 400 with `IndexedErrorMessage {code, message, failures:[{index, message}]}` (`indexed_bad_request`).
- Unknown route, or `chain_filter` before genesis observed => 404 (`NOT_FOUND: Beacon chain genesis has not yet been observed.`). Network senders missing => 404 `The networking stack has not yet started`.
- Queue overload (BN processor API queues full, 1024 each for P0 and P1, `beacon_processor/src/scheduler/work_queue.rs`) => 500 `INTERNAL_SERVER_ERROR: The task was dropped. The server is overloaded.` (`task_spawner.rs` `send_to_beacon_processor`). Not a 503, no rate limiting otherwise.
- `--http-enable-beacon-processor` (default true) queues API work in the beacon processor: P0 = validator-critical (duties, block/attestation production, node/syncing, events), P1 = everything else; `false` runs on tokio directly.

### 503 / syncing
- `not_while_syncing_filter` (lib.rs): returns 503 only when sync state is `SyncingFinalized|SyncingHead` AND `head_slot + sync_tolerance_epochs*slots_per_epoch < current_slot`. `sync_tolerance_epochs` default 2 (`--sync-tolerance-epochs`, `beacon_chain/src/chain_config.rs`). BackFill/CustodyBackFill/SyncTransition/Synced/Stalled never 503. Applied to validator endpoints: duties (proposer/attester/sync/ptc), `blocks`, `blinded_blocks`, `attestation_data`, `aggregate_attestation`, `sync_committee_contribution`, `aggregate_and_proofs`, `contribution_and_proofs`, `prepare_beacon_proposer`, `payload_attestation_data`, envelope/block v4 routes. NOT applied to `beacon/*`, `debug/*`, `node/*`, pool POSTs, `register_validator`, `beacon_committee_subscriptions`.
- `GET /eth/v1/node/syncing` always 200 with `{head_slot, sync_distance, is_syncing, is_optimistic, el_offline}`; `is_syncing = !(Synced || (Stalled && target_peers==0))`. `el_offline` comes from `is_el_offline` (EL offline/erroring; with no EL and no EIP-8025 proofs configured it is true).
- `GET /eth/v1/node/health`: 503 if EL offline (`execution layer is offline`), 206 if syncing or head optimistic, else 200. Syncing alone is 206 not 503.
- No "optimistic => 503" gate on validator endpoints. Optimistic head matters via `execution_optimistic` flags, `filter_optimistic_attestation` / `filter_optimistic_sync_committee_contribution` (`beacon_chain.rs`; aggregates/contributions referencing non-fully-verified blocks error `HeadBlockNotFullyVerified`) and builder gating (`ChainHealth::Optimistic` => no builder).

### state_id / block_id
- Parsing: `common/eth2/src/types.rs` `StateId::from_str` / `BlockId::from_str`: `head|genesis|finalized|justified`, `0x`-prefixed root, else decimal slot; anything else => 400 `Invalid state ID` / `Invalid block ID`. Resolution: `http_api/src/state_id.rs` (`StateId::root`, `state`, `map_state_and_execution_optimistic_and_finalized`) and `block_id.rs` (`BlockId::root`, `blinded_block`, `full_block`).
- `justified` block/state returns `finalized=false`; `finalized` => true; `head` => false; `genesis` => true. Slot id: `finalized = slot <= finalized_epoch.start_slot`. `execution_optimistic` for slot ids = whether the *head* is optimistic (coarse); for roots uses fork-choice node status (`is_optimistic_or_invalid_block_assuming_full`); for checkpoints with epoch < finalized uses finalized block's status.
- Block by root: `0x00..00` => 404 (deliberately matches Teku); skipped slot => 404 `beacon block at slot N`. Block can also be resolved through `early_attester_cache` before DB write.
- State availability (non-`--archive` default): hot DB states since the split slot (~finalized) are served; older slots => 404 `beacon state at slot N` (`BeaconChain::state_root_at_slot` returns None between historic lower/upper limits; non-archive sets `state_upper_limit = STATE_UPPER_LIMIT_NO_RETAIN`, `store/src/metadata.rs`, so finalized non-genesis states are not kept in freezer, `hot_cold_store.rs` migrate path `if slot != 0 && slot < anchor_info.state_upper_limit { continue; }`). Genesis state always available. By state root: hot summary or cold slot index, else 404 `beacon state for state root`.
- `--archive` (alias `--reconstruct-historic-states`, `beacon_node/src/cli.rs`): keep all states; after checkpoint sync + backfill to genesis, `store/src/reconstruct.rs` `reconstruct_historic_states` rebuilds them (starts only once backfill is complete; pauses hot->cold migration while running; also triggerable via `POST /lighthouse/database/reconstruct`). `book/src/advanced_checkpoint_sync.md`. Needed for `/lighthouse/validator_inclusion` and old state queries. Checkpoint-synced nodes have no states below the checkpoint anchor and blocks only back to wherever backfill reached (`--genesis-backfill` forces to genesis).
- Cold states use hierarchical diffs: `--hierarchy-exponents` default `5,9,11,13,16,18,21` (immutable after DB init; stored in `OnDiskStoreConfig`), snapshots every 2^21 slots, per-epoch diffs 2^5. Replay for sub-diff slots. Caches: `--state-cache-size 128`, `--historic-state-cache-size 1`, `--hdiff-buffer-cache-size 16`, `--hot-hdiff-buffer-cache-size 1`, `--block-cache-size 0`. `--slots-per-restore-point` is deprecated no-op. `book/src/advanced_database.md`. Hot->cold migration every `--epochs-per-migration` (default 1).
- Committees for old epochs use `HistoricalCommitteeCache` (`http_api/src/caches.rs`, `Config.historical_committee_cache_size`).

### Content negotiation / headers
- Request `Accept`: `common/eth2/src/types.rs` `Accept::from_str` (q-factor aware; `application/octet-stream` => SSZ, `application/json`, `*/*`). Handlers match `Some(Accept::Ssz)`, everything else (including missing/any/json) gives JSON. Unparseable Accept => 400 `invalid Accept header`. Supported SSZ GETs: blocks, blinded_blocks, blob_sidecars, blobs, debug states, data_column_sidecars, light client objects, attestation_data, validator block production, validator identities.
- Responses set `Content-Type: application/octet-stream` for SSZ and `Eth-Consensus-Version` (`add_consensus_version_header`) on fork-dependent GETs (SSZ and JSON). JSON v2/v3 bodies carry `version`, v1 bodies do not (but see quirks).
- POST bodies: JSON default; SSZ requires `Content-Type: application/octet-stream` and the SSZ route set. `Eth-Consensus-Version` header is REQUIRED on block POSTs (`consensus_version_header_filter`), used to decode (`PublishBlockRequest::context_deserialize / from_ssz_bytes`); body fork disagreeing => 400 `invalid JSON/SSZ`. `POST /eth/v2/beacon/blocks?broadcast_validation=gossip|consensus|consensus_and_equivocation` (default `gossip`).
- `execution_optimistic` and `finalized` appear on all state/block-id based responses via `execution_optimistic_finalized_beacon_response` / `GenericResponse::add_execution_optimistic_finalized`.
- Block publish result (`publish_blocks.rs`): success 200; already-known block => `--http-duplicate-block-status` (default 202) message `duplicate block`; with default `gossip` validation, a block that is broadcast but fails import returns 202 `ACCEPTED: the object was broadcast to the network without being fully imported ...` (`broadcast_without_import`); with `consensus*` validation failures are 400 `Invalid block: ...`; slashable proposal => 400 `proposal for this slot and proposer has already been seen`; publish channel failure => 500.

### SSE `/eth/v1/events`
- Handler `get_events` (lib.rs), topics enum `EventTopic` in `common/eth2/src/types.rs`; broadcaster `beacon_chain/src/events.rs` `ServerSentEventHandler`. Topics: `head`, `head_v2`, `block`, `block_gossip`, `blob_sidecar`, `data_column_sidecar`, `attestation`, `single_attestation`, `voluntary_exit`, `finalized_checkpoint`, `chain_reorg`, `contribution_and_proof`, `payload_attributes`, `light_client_finality_update`, `light_client_optimistic_update`, `attester_slashing`, `proposer_slashing`, `bls_to_execution_change`, `execution_payload`, `execution_payload_gossip`, `execution_payload_available`, `execution_payload_bid`, `proposer_preferences`, `payload_attestation_message`, `fast_confirmation`, `inclusion_list`. Unknown topic => 400 (`event topic cannot be parsed.`).
- Backpressure: one `tokio::sync::broadcast` channel per topic, capacity `512 * --http-sse-capacity-multiplier` (default 1). Slow consumer gets an SSE comment `error - dropped N messages` and the stream stays open (messages dropped, not disconnected). Keep-alive via `warp::sse::keep_alive()`. Response headers disable nginx buffering (`X-Accel-Buffering: no`, `Cache-Control: no-cache...`). If event handler uninitialised => 500.

### Blobs / data columns
- Retention: `ChainSpec::min_epoch_data_availability_boundary` (`consensus/types/src/core/chain_spec.rs`): `min_epochs_for_blob_sidecars_requests` (default 4096) pre-Fulu, then `min_epochs_for_data_column_sidecars_requests` (default 4096; Gnosis config sets 16384) once the blob retention epoch passes the Fulu fork epoch. Pruning: `store/src/hot_cold_store.rs` `try_prune_blobs` / `try_prune_most_blobs`; flags `--prune-blobs` (default true), `--epochs-per-blob-prune` (CLI default 256; the `StoreConfig` const default 1 is overridden by the CLI), `--blob-prune-margin-epochs` (0). `--complete-blob-backfill` (hidden) forces `prune_blobs=false`. Separate blobs DB dir: `--blobs-dir`. Pruning only runs up to the split (finalization).
- Custody: `--supernode` (custody all columns, alias `--subscribe-all-data-column-subnets`), `--semi-supernode` (half, enough to reconstruct), default = `custody_requirement` 4 groups (mainnet) increased by attached validators' balance (validator custody, `beacon_chain/src/custody_context.rs`; `balance_per_additional_custody_group`; docs say >=2048 ETH => semi-supernode, >=4096 => supernode). Inspect with `GET /lighthouse/custody/info`; `POST /lighthouse/custody/backfill`.
- `GET /eth/v1/beacon/blob_sidecars/{id}` (`get_blob_sidecars`, `BlockId::get_blinded_block_and_blob_list_filtered`): pre-Deneb block => 400 `block is pre-Deneb and has no blobs`; block with zero commitments => 200 `[]`; pre-Fulu => read from blobs DB, if pruned/missing => 404 `no blobs stored for block {root}`; post-Fulu (`is_peer_das_enabled_for_epoch`) => reconstructed from stored columns (`beacon_chain::kzg_utils::reconstruct_blob_sidecars`) and needs >= 50% of columns (`number_of_columns()/2`), else 400 `Insufficient data columns to reconstruct blobs: required N, but only M were found. You may need to run the beacon node with --supernode or --semi-supernode.`; reconstruction failure => 500. `indices` query filters (invalid/out-of-range indices silently dropped).
- `GET /eth/v1/beacon/blobs/{id}?versioned_hashes=..` (`get_blobs`, `get_blobs_by_versioned_hashes`): returns raw blobs ordered by KZG commitment order (not request order); same 400/404 rules. JSON response has no version field; SSZ body is the list of blobs.
- `GET /eth/v1/debug/beacon/data_column_sidecars/{id}` (`BlockId::get_data_columns`): pre-Fulu => 400 `block is pre-Fulu and has no data columns`; returns only columns THIS node custodies/has (empty list 200 if pruned or not custodied; `indices` filter via `get_data_columns_checking_all_caches`).
- Missing blob/column data affects import: `data_availability_checker` (`beacon_chain/src/data_availability_checker.rs`), `fetch_blobs/mod.rs` (calls EL `engine_getBlobsV2/V3/V4` to skip waiting for gossip; disable with `--disable-get-blobs`). Blob API on non-Fulu `publish`: `MissingComponents` => 202/400 per validation level.

### Light client, rewards, misc
- Light client server enabled by default; `--disable-light-client-server` makes `beacon/light_client/*` 404 (`light_client_server_filter`). `updates?start_period&count` count capped at 128 (`MAX_REQUEST_LIGHT_CLIENT_UPDATES`), none found => 404 `No LightClientUpdates found`. `beacon/light_client/*` supports SSZ.
- Rewards: `standard_block_rewards.rs` (blocks), `beacon/rewards/attestations/{epoch}`, `sync_committee_rewards.rs`; need the relevant state, so old epochs fail on non-archive nodes (unverified exact status).
- Validator production gating: `attestation_data` ignores the `committee_index` query (always 0; electra+), rejects slots > current+1 with 400.

### CORS / limits / timeouts
- CORS (`warp_utils::cors::set_builder_origins`): methods GET+POST, header `Content-Type`; origin = `--http-allow-origin` (comma list or `*`) else only `http://<listen_addr>:<port>`. TLS experimental: `--http-enable-tls --http-tls-cert --http-tls-key`.
- No built-in request timeout, auth, or rate limiter on the BN HTTP API (bind to localhost, proxy externally). `Server: Lighthouse/vX-<commit>/<platform>` header on all responses. Prometheus per-path counters in `prometheus_metrics()` of lib.rs; logs via `tracing_logging()` (success=debug, non-2xx=warn).
- The client side timeouts used by VC are in `common/eth2` `Timeouts` and `validator_client/src/config.rs` (`--use-long-timeouts`, `--long-timeouts-multiplier`).

## 4. Engine API client (beacon_node/execution_layer)

- `src/engine_api/http.rs` `HttpJsonRpc`: constants for methods and timeouts (all multiplied by `--execution-timeout-multiplier`, default 1). `engine_newPayloadV1..V6` (V3 deneb, V4 electra/fulu, V5 gloas, V6 heze) timeout 8s; `engine_getPayloadV1..V6` 2s; `engine_forkchoiceUpdatedV1..V5` 8s (V4/V5 also pass custody columns for EL sparse blobpool, EIP-8070); `engine_getPayloadBodiesByHashV1/V2` 10s; `engine_getBlobsV2/V3/V4` 1s; `engine_getInclusionListV1` 1s; `engine_exchangeCapabilities` 1s; `engine_getClientVersionV1` 1s; `eth_syncing` 1s; `eth_getBlockByNumber` 1s.
- Version selection is automatic by fork + `engine_exchangeCapabilities` (`new_payload`, `get_payload`, `forkchoice_updated` dispatchers in `http.rs`); unsupported required method => `RequiredMethodUnsupported("engine_...")`. Capabilities and client version are cached with an age limit and refreshed by `Engine::upcheck`.
- High level: `src/lib.rs` `ExecutionLayer::{notify_new_payload, notify_forkchoice_updated, get_payload, determine_and_fetch_payload, get_blobs_v2/v3/v4, propose_blinded_beacon_block, get_payload_bodies_by_hash}`; `src/engines.rs` `Engine` state machine `Synced|Syncing|Offline|AuthFailed` (`request()` wraps every call; success when not Synced spawns an upcheck; error spawns upcheck). No automatic retry of the failed call; recovery relies on the upcheck loop (`upcheck` runs `eth_syncing`; on coming back Online it re-sends the latest forkchoice state). Single EL endpoint only (`--execution-endpoint`, alias `--execution-endpoints` but exactly one value is accepted, `parse_only_one_value`).
- Result handling: `src/payload_status.rs` `process_payload_status`: VALID requires `latestValidHash == block hash` else `BadResponse` error; INVALID/INVALID_BLOCK_HASH/SYNCING/ACCEPTED mapped to `PayloadStatus`. Beacon chain side: `beacon_chain/src/execution_payload.rs` `notify_new_payload`: VALID => `Verified`; SYNCING|ACCEPTED => `Optimistic` (block imported optimistically; no safe-slots gate; `UnverifiedNonOptimisticCandidate` error variant exists but is unused); INVALID => if `latestValidHash` non-null and non-zero, `process_invalid_execution_payload(InvalidateMany{...})` in `beacon_chain.rs` (invalidates ancestors in fork choice) then block rejected `RejectedByExecutionEngine`; INVALID_BLOCK_HASH => block rejected only; transport/auth errors => `ExecutionPayloadError::RequestFailed` (block import fails; not treated as optimistic). `update_execution_engine_forkchoice` (`beacon_chain.rs`) holds a global lock so FCUs are ordered; handles re-org override of FCU; `--always-prepare-payload`, `--prepare-payload-lookahead` tune payload-attribute prep.
- Fee recipient mismatch from `engine_getPayload` only logs an error (`Inconsistent fee recipient`), it does not fail.
- Optimistic sync state: `fork_choice`/`proto_array` execution status (`Optimistic|Valid|Invalid|Irrelevant`); surfaced by `is_optimistic_or_invalid_head()`; `--reset-payload-statuses`, `--disable-optimistic-finalized-sync` flags exist.
- JWT: required with `--execution-endpoint`. `--execution-jwt <file>` (hex secret, aliases `--jwt-secrets`) or `--execution-jwt-secret-key <hex>` (written to a file in datadir; conflicts with `--execution-jwt`); neither => hard error (no default path). Optional `--execution-jwt-id`, `--execution-jwt-version` (claims `id`/`clv`). Token logic in `src/engine_api/auth.rs` (HS256, 32-byte key, `iat` claim). Auth failure => engine `AuthFailed` (counts as Offline for `el_offline`).
- Other EL flags: `--suggested-fee-recipient` (BN fallback only; VC value wins), `--proof-engine-endpoint` (EIP-8025, experimental, makes `--execution-endpoint` optional).
- `book` docs for the EL: `book/src/run_a_node.md`.

Missing header => 401, wrong => 403. Flags: `--http`, `--http-address` (default 127.0.0.1; non-loopback requires `--unencrypted-http-transport`), `--http-port` 5062, `--http-allow-origin`, `--http-allow-keystore-export`, `--http-store-passwords-in-secrets-dir`. Tests: `validator_client/http_api/src/tests.rs`, `tests/keystores.rs`.
- Builder (MEV-boost) BN side: `--builder <url>` (aliases `--payload-builder(s)`), single builder only (use mev-boost for many). Code: `beacon_node/builder_client/` (`pre_gloas_builder_http_client.rs`: default timeout 15s, get_header 1000ms; `builder_http_client.rs` Gloas: bid fetch 400ms, submit 1000ms; `--builder-header-timeout` default 1000ms, max 3000ms; `--builder-disable-ssz`, `--builder-user-agent`), logic in `execution_layer/src/lib.rs` `determine_and_fetch_payload` and `verify_builder_bid`.
- Local vs builder payload (pre-Gloas): builder and local payloads are fetched concurrently (`fetch_builder_and_local_payloads`). Fallback to LOCAL when: no builder configured; chain health != Healthy (`ChainHealth::{Unhealthy(cond), Optimistic, PreMerge}`); builder error; builder returns no bid; invalid bid (`verify_builder_bid` fails, counted in `EXECUTION_LAYER_GET_PAYLOAD_BUILDER_REJECTIONS`); `local_value >= relay_value/100*boost`; EL `shouldOverrideBuilder`. If builder ok but local fails, builder payload is used. Both fail => `CannotProduceHeader` (missed proposal).
- Chain-health circuit breaker flags (`beacon_chain/src/chain_config.rs`): `--builder-fallback-skips` 3, `--builder-fallback-skips-per-epoch` 8, `--builder-fallback-epochs-since-finalization` 3, `--builder-fallback-ban-slots` 32 (`--builder-fallback-disable-checks` turns off).
- Boost factor: API param `builder_boost_factor` on `GET /eth/v3/validator/blocks/{slot}`; value 100 is normalised to `None` (`produce_block.rs` `DEFAULT_BOOST_FACTOR`). Semantics: `boosted_relay = relay_value / 100 * factor` (saturating); 0 => always local, `u64::MAX` => effectively always builder (unless EL says override). VC mapping in `validator_client/lighthouse_validator_store/src/lib.rs` `determine_builder_boost_factor`: per-validator `prefer_builder_proposals` => MAX; per-validator `builder_boost_factor`; per-validator `builder_proposals=false` => 0; else global `--prefer-builder-proposals` => MAX, `--builder-boost-factor`, and `!--builder-proposals` => 0 (VC default is local-only unless `--builder-proposals`). VC registers validators (`register_validator`, batch size `--validator-registration-batch-size` default 500, gas limit `--gas-limit`/per-validator, default 60M `DEFAULT_GAS_LIMIT`, or schedule from Gloas). `GET v3 blocks` response headers `Eth-Execution-Payload-Blinded`, `Eth-Execution-Payload-Value`, `Eth-Consensus-Block-Value`.
- Blinded blocks: `POST /eth/v1|v2/beacon/blinded_blocks` => `publish_blinded_block`: local payloads are reconstructed from the EL payload cache; builder payloads are submitted to the builder (`propose_blinded_beacon_block`), which returns the full payload.
- Gloas (ePBS) builder path: `POST v4/validator/blocks/{slot}` takes VC `BuilderConfig` body (JSON or SSZ by Content-Type, requires `Eth-Consensus-Version`), selection in `beacon_chain/src/block_production/bid_selection.rs` and `gloas.rs`; response headers `Eth-Execution-Payload-Included`, `Eth-Builder-Url`. `GET v3 blocks` for a Gloas slot => 400 `Gloas block production requires POST v4/validator/blocks`. Book: `book/src/gloas_builder_config.md`, `advanced_builders.md`.
- Block production errors from the chain are flattened into 400 `failed to fetch a block: <Debug>` (`produce_block_v3`), not 500 (quirk).

## 6. Quirks and deviations from beacon-APIs spec / other clients

- Many "v1" endpoints that are versioned in the spec behave inconsistently: `get_blob_sidecars` (v1) and `debug/data_column_sidecars` return a `version` field in JSON; `debug/beacon/states/{id}` accepts any version (v1 and v2) and always returns a versioned body.
- Default `broadcast_validation=gossip` on v2 publish: failures after broadcast still return 202 not 4xx; the v1 publish endpoints always use `gossip` validation.
- `/eth/v1/node/syncing` never returns 503; use `/node/health` for 200/206/503 semantics. `/node/health` returns 206 when head is optimistic.
- Block by zero root => 404 (Teku-compatible); `blob_sidecars` for pruned blobs => 404 (not empty list), for blocks without blobs => 200 `[]`.
- Block production `attestation_data` ignores committee index; `GET proposer duties` v1 returns legacy dependent root, v2 the true fork-aware root (post-Fulu epoch N-2).
- State endpoints for non-archive nodes only cover roughly finalized-and-newer states (+ genesis); other clients may keep more or serve via different pruning. Reconstruction is opt-in (`--archive`). State by `justified` and `finalized` resolve through the checkpoint slot (epoch start) and its root's execution status.
- `execution_optimistic` for slot-based ids reflects the head, not the specific block.
- Event topics include many non-standard/experimental ones (Gloas/ePBS, `fast_confirmation`, `inclusion_list`, `head_v2`, `block_gossip`); SSE drops messages instead of disconnecting.
- Doc comment in `execution_layer/src/lib.rs` on `notify_forkchoice_updated` says "Maps to the `engine_consensusValidated` JSON-RPC call"; it actually issues `engine_forkchoiceUpdated` (stale comment).
- BN HTTP API has no auth; VC keymanager does. HTTP server is warp inside an axum router (migration in progress, `Error::Warp` and axum `BuilderError` both exist).
